# OpenCode Go 用量预测与套餐额度组件设计

本文讨论两件事：如何根据当前请求记录预测未来的按量费用，以及如何预测 Go 套餐的 5 小时、周、月额度消耗。设计只涉及新增组件和数据口径，不要求修改现有请求日志字段。

## 1. 设计结论

预测组件不能只维护一个“当前每小时花多少钱”的数字。至少要同时维护三条独立的数据链：

1. 官方返回的套餐额度快照，包括共享计划额度和三个时间窗口的已用量、上限、重置时间。
2. 每条请求按 Go 套餐价格表折算出的额度消耗。
3. 基于历史请求的时间序列预测出的未来增量。

现金费用和套餐额度必须分开显示。请求日志中的 `costUsd` 适合表示按量费用，但不能直接当作 Go 套餐额度。Go 文档明确说明，套餐按模型有自己的价格表和月额度；同一个请求用 DeepSeek 和 GPT 计算出的额度消耗不同，模型额度的上限也不同。

最终组件应当回答四个问题：

- 当前选中的历史范围内，实际花了多少。
- 按照最近的节奏，下一个 1 小时、24 小时和到重置前预计会花多少。
- 当前套餐的三个共享窗口各用了多少，预计何时触顶，重置时还剩多少。
- 哪个模型最可能成为限制项，以及它是被模型自身额度限制，还是被套餐共享额度限制。

前三个问题可以使用同一套预测引擎，第四个问题必须使用“模型额度 + 共享计划额度”的双层约束计算。

## 2. 项目现状对设计的约束

当前项目的请求记录已经包含时间、模型、供应商、Token 明细和官方费用，足以做预测。现有数据结构的关键字段包括：

- `startedAt`：请求开始时间，作为时间序列和额度的归属时间。
- `model`、`provider`：模型识别和价格匹配的入口。
- `inputTokens`、`outputTokens`、`reasoningTokens`。
- `cacheReadTokens`、`cacheWriteTokens`、`cacheWrite1hTokens`。
- `costUsd`：当前控制台请求日志中的费用字段。
- `outcome`：成功、失败、拒绝、取消。

当前页面已经有 `1h`、`24h`、`7d`、`30d`、`all` 和自定义范围。`1h` 使用 5 分钟桶，`24h` 使用小时桶，`7d` 和 `30d` 使用天桶。这个分桶方式可以直接复用，但预测需要额外读取比当前展示范围更长的历史数据。

例如用户正在看 `1h` 视图时，当前面板只加载最近一小时记录，这不足以计算周额度和月度模型上限。预测组件应当独立加载至少最近 28 天，或加载当前套餐窗口覆盖的范围：

```text
预测历史起点 =
  min(当前展示范围起点,
      当前 5 小时窗口起点,
      当前 UTC 周起点,
      当前付费周期起点,
      now - 28 天)
```

如果本地历史存在缺口，预测仍然可以运行，但必须降低置信度并显示数据覆盖率，不能把缺失当成零消费。

## 3. 费用和套餐额度是两个口径

### 3.1 按量费用

`cost` 或 `costUsd` 是请求日志提供的费用字段。它可以用于：

- 展示历史按量费用。
- 预测未来的按量账单。
- 和支付余额、额外用量做对比。

它不能直接用于计算 Go 套餐额度，除非已经用真实请求验证过该字段就是 Go 额度折算值。

### 3.2 套餐额度

Go 套餐的额度单位虽然也显示为美元，但它是套餐价格表折算出来的消费单位。每条请求应计算一个独立的 `quotaUsd`：

```text
quotaUsd(r) =
  inputTokens        / 1,000,000 * inputPrice
+ outputTokens       / 1,000,000 * outputPrice
+ cacheReadTokens    / 1,000,000 * cacheReadPrice
+ cacheWriteTokens   / 1,000,000 * cacheWritePrice
+ cacheWrite1hTokens / 1,000,000 * cacheWrite1hPrice
```

价格使用 Go 套餐表，不使用普通按量价格表。模型有上下文阈值、Peak/Off-Peak、免费模型和促销额度时，必须先确定价格变体，再套用公式。

`reasoningTokens` 是否已经包含在 `outputTokens` 中，需要在实现前用真实账单核对。没有确认前，不能把它再次加到 output 里，否则会重复计费。

### 3.3 两层额度约束

Go 文档和控制台的额度状态至少提供了两层信息。

第一层是共享计划额度。当前 Go 计划的状态对象提供三个 meter：

```text
fiveHour: usedMicroCents, limitMicroCents, startsAt?, resetsAt
week:     usedMicroCents, limitMicroCents, resetsAt
month:    usedMicroCents, limitMicroCents, resetsAt
```

按当前公开配置，Go 的共享上限为 5 小时 12 美元、周 30 美元、月 60 美元；Go Plus 为 5 小时 48 美元、周 120 美元、月 240 美元。5 小时窗口从首次使用开始计时，控制台显示为 Rolling；周窗口按 UTC 日历周，月窗口按付费周期。组件应优先使用 API 返回的 `resetsAt`，不要自己假设本地时间的月末。

第二层是模型额度。Go 文档表格中的 `Monthly limit` 是模型自身的月额度，5 小时和周额度分别为该模型月额度的 20% 和 50%。例如当前文档中 DeepSeek V4.1 Flash 的月额度为 80 美元，GPT 5.6 Luna 为 15 美元。模型的 Peak/Off-Peak 变体、上下文阈值变体共享同一个模型额度组。

这两层约束同时存在：

- 共享额度是套餐的总表，所有模型消耗都会累计到它。
- 模型额度是单模型的限制，某个模型即使没有耗尽总表，也可能先耗尽自己的额度。
- 模型额度是上限，不意味着不同模型的上限可以合并或转移。
- DeepSeek 的模型上限可能高于共享月上限，这时共享计划表先成为限制。
- GPT 这类模型上限较低，即使总表还有余额，也可能先被模型上限拦住。

因此界面不能只显示一个按月总额度算出的百分比。正确做法是同时维护计划级风险和模型级风险，并显示最早触发的约束。

### 3.4 为什么不能按现金价格统一判断

同样花费 10 美元的现金账单，不代表消耗了同样多的套餐额度。套餐额度要用 Go 价格表逐请求折算。文档给出的典型请求可以说明差异：

| 模型 | 典型请求 Token | Go 额度消耗 |
|---|---:|---:|
| DeepSeek V4.1 Flash Off-Peak | 410 input、71,300 cached、310 output | 约 0.000461 美元 |
| GPT 5.6 Luna ≤ 272K | 1,000 input、50,000 cached、220 output | 约 0.001464 美元 |

在这个例子里，同样一条典型请求，DeepSeek 只消耗 GPT 约 31.5% 的套餐额度。DeepSeek 的模型月上限是 80 美元，GPT 是 15 美元，模型额度又把差异放大。预测组件必须先计算 `quotaUsd`，再汇总和预测，不能先按 `costUsd` 汇总模型费用，再套一个统一价格。

## 4. 价格目录

价格不能硬编码在 UI 组件里。建议增加一个带版本号的 `PlanCatalog`，由文档同步或人工更新维护：

```ts
interface PlanCatalog {
  version: string;
  sourceUrl: string;
  retrievedAt: number;
  plans: {
    go: PlanDefinition;
    'go-plus': PlanDefinition;
  };
  models: ModelPriceGroup[];
}
```

每个模型价格组包含：

```ts
interface ModelPriceGroup {
  group: string;                 // 例如 deepseek-v4.1-flash
  aliases: string[];             // API 中可能出现的模型名
  monthlyLimitUsd: number;
  variants: PriceVariant[];
}

interface PriceVariant {
  input: number;
  output: number;
  cacheRead: number;
  cacheWrite: number;
  cacheWrite1h?: number;
  contextLimit?: number;         // 例如 272K
  peak?: PeakRule;               // 例如 DeepSeek 的 UTC 时段
  validFrom?: number;
  validUntil?: number;
  promoLabel?: string;
}
```

需要特别处理的规则：

- `DeepSeek V4.1 Flash` 和 `V4 Pro`：UTC 周一至周五 01:00–04:00、06:00–10:00 为 Peak，其余时间为 Off-Peak。
- `GPT`、`Grok`、`Claude Haiku`、`Qwen3.7 Plus` 等有输入上下文阈值，超过阈值后使用另一组价格。
- `Step 5 Preview` 和 `Gemini 4 Argon Contributor` 当前存在限时倍数额度，必须记录促销有效期，不能把促销值永久写入。
- 免费模型不消耗套餐额度，但仍应保留在请求明细中。
- 未知模型不能静默套用一个平均价格。标记为 `unpriced`，在预测结果中显示未覆盖的请求数量或费用占比。

价格表中的金额建议使用整数微美元或微美分。当前项目已有 `MICROCENTS_PER_DOLLAR = 1e8`，套餐 meter 也是 `usedMicroCents` / `limitMicroCents`，可以直接统一到这个单位，避免浮点累计误差。

## 5. 每次请求如何匹配价格

处理顺序建议固定为：

1. 用 `provider + model` 做精确匹配。
2. 用模型别名和规范化名称做匹配。
3. 判断是否属于同一模型额度组。Peak/Off-Peak 和上下文阈值变体必须归入同一组。
4. 根据上下文长度选择价格变体。上下文长度至少应包含输入、缓存读、缓存写；是否包含 output 需要与官方计费语义核对。
5. 根据 `startedAt` 的 UTC 时间判断 Peak/Off-Peak。
6. 根据请求的 Token 字段计算 `quotaUsd`。
7. 记录匹配到的 `priceVersion`，方便以后解释一次预测为什么发生变化。

免费、未知、旧版记录分别处理：

- 免费模型：`quotaUsd = 0`，但保留 `priced = true`。
- 未知模型：`priced = false`，不参与额度预测，并在 UI 中显示覆盖缺口。
- 旧版记录：如果没有完整 Token 字段，可以继续参与现金预测，但不能参与套餐额度预测。

## 6. 预测模型

### 6.1 展示范围不等于预测跨度

当前下拉框选择的是“历史展示范围”，不应该直接决定未来预测跨度。`1h` 视图不意味着只预测下一小时，也不意味着把最近一小时乘以 24；`30d` 视图也不意味着一定要预测未来 30 天。

建议把两个概念拆开：

- `analysisRange`：当前历史的起点和终点，用于图表和聚合。
- `forecastHorizon`：未来要预测多久，可选项为下一小时、未来 24 小时、当前窗口结束、本周结束、本月重置。

为了减少界面复杂度，可以给每个历史范围设置默认预测跨度，同时允许用户覆盖：

| 当前视图 | 历史数据 | 默认预测 | 主要用途 |
|---|---|---|---|
| 1h | 5 分钟桶，结合 28 天历史 | 下一小时；同时显示当前 5 小时窗口风险 | 观察当前会话和短期突发 |
| 24h | 小时桶，结合 28 天历史 | 未来 24 小时；同时显示周额度风险 | 预测当天或下一日消费 |
| 7d | 天桶，结合 28 天历史 | 本周重置前；同时显示月额度风险 | 判断本周是否超额 |
| 30d | 天桶，结合 28 天历史 | 本月重置前 | 判断月度额度和剩余量 |

这样，用户在 `1h` 页面看到的是“过去一小时 + 下一小时”的连续曲线，而不是一个被放大的日均值。用户在 `24h` 页面看到的是“过去 24 小时 + 未来 24 小时”，预测会按小时使用不同的日周期权重。

### 6.2 基础预测模型

推荐使用可解释的稳健模型，不引入后端服务，也不依赖复杂的机器学习库。

对每个模型额度组或总费用序列，按预测跨度选择桶大小：

- 预测 1 小时：5 分钟桶。
- 预测 24 小时：1 小时桶。
- 预测 7 天：1 小时或 1 天桶，按周内模式聚合。
- 预测到月重置：1 天桶加小时/周内模式。

模型由三部分组成：

```text
未来某个时间桶的预测值
  = 最近的稳健水平
  × 该时间桶的周期性因子
  × 长周期趋势因子
```

周期因子使用最近 28 天的同类时间桶。例如预测周二 14:00–15:00，就使用历史上周二同一小时的中位数或截尾均值。样本不足时向全局平均值收缩，避免一个偶然的尖峰成为周期基准。

最近水平使用指数加权移动平均。权重按预测跨度调整：

- 1 小时预测更重视最近 15–30 分钟。
- 24 小时预测更重视最近 6–12 小时。
- 数天预测更重视最近 2–5 天。
- 月重置预测使用最近 5–7 天的水平，但必须叠加周内周期。

长周期趋势只在预测超过 24 小时时启用。用最近 3–7 天的日总量做稳健斜率，限制在合理区间并向 1 收缩，避免一次异常爆发把整月预测拉高。

对 1 小时预测，可以额外考虑当前会话是否仍在活跃。项目记录中有 `sessionID`，可以用历史会话的持续时间和请求间隔估计“当前会话继续产生请求”的概率。这个能力可以作为第二阶段加入，第一版不必依赖它。

对套餐额度，所有预测都按模型组分别计算，再汇总到计划表。不要先预测一个统一美元总额，再用平均价格拆分到模型。模型混合比例本身可能变化，独立预测才能正确处理。

### 6.3 1h、24h、30d 的具体处理

**1h 视图**

使用最近 5 分钟、15 分钟、60 分钟三个速率估计值，去掉异常桶后进行加权。下一小时的 12 个 5 分钟桶再乘以同星期、同小时、同 5 分钟位置的周期因子。当前会话活跃时提高短期估计权重；没有最近活动时降低点预测值，并扩大置信区间。不要在 1h 视图里把最近一小时直接乘以 24 作为日预测。

**24h 视图**

使用过去 24 小时判断当前水平，但未来 24 小时按小时槽逐个预测，不能简单地“今天总量 = 昨天总量”。例如夜间和白天、工作日和周末的请求密度不同，小时周期必须参与。对套餐额度，还要单独计算 5 小时窗口和 UTC 周窗口的剩余风险。

**7d 和 30d 视图**

使用日总量和周内周期，叠加近期趋势。30 天预测到月重置时，使用“从现在到重置”的实际小时数，不要固定乘 30。重置时间从套餐 meter 的 `resetsAt` 读取；如果用户只是选择了一个自定义历史范围，预测跨度仍由预测控件决定。

### 6.4 置信区间和降级策略

点预测不足以支撑“额度会不会提前耗尽”的判断。建议保留 `p10`、`p50`、`p90` 三个值：

- `p50` 用于主文案。
- `p90` 用于风险提示，表示偏保守的消耗上界。
- `p10` 用于剩余额度下界。

置信区间可以通过滚动回测得到：在最近 14 天里，选取多个历史起点，只使用起点之前的数据做同样跨度的预测，记录实际值和预测值的比例，再取经验分位数。样本不足时使用固定宽度区间，并把置信度降为“低”。

降级顺序：

1. 有 28 天且无明显缺口：使用完整周期 + 趋势。
2. 有 7–28 天：使用周期 + 最近水平，趋势弱化。
3. 有 24 小时以上：退回最近 24 小时水平 + 日周期。
4. 有 1 小时以上：退回最近一小时水平，短时预测仍然可用，长时预测标记不可靠。
5. 没有有效记录：只显示官方 meter 的已用和上限，不显示“0 元预测”。

## 7. 套餐额度预测

### 7.1 统一额度事件

每条 priced 请求生成一个额度事件：

```text
event = {
  timestamp: startedAt,
  modelGroup: canonicalModel,
  quotaUsd: computedQuotaUsd,
  requestId
}
```

所有预测都基于事件，而不是基于 `costUsd`：

```text
计划窗口已用 = 官方 meter.usedMicroCents / 1e8
模型窗口已用 = 该窗口内该模型额度事件之和
```

如果官方 meter 与本地事件合计不一致，优先信任官方 meter 的总已用量。差额可能来自本地数据缺口、旧版记录、价格表变化或请求日志延迟。对计划级预测，直接使用“官方已用 + 未来增量”，不要再把本地已用加到官方值上。

对模型级预测，需要做差额处理：

- 如果本地覆盖率足够且差额很小，按本地模型分布估算。
- 如果差额较大且只有一个模型有记录，可以把差额归给该模型，但标记为估算。
- 如果有多个模型且无法确定差额来源，显示“模型级已用为估算”，不承诺精确的模型耗尽时间。

### 7.2 计划级耗尽时间

对某个共享窗口 `w`：

```text
U_w(t) = 官方已用 + 从当前时刻到 t 的预测额度增量
t_exhaust(w) = min { t | U_w(t) >= limit_w }
remaining_w(R) = max(0, limit_w - U_w(R))
```

其中 `R` 是该窗口的 `resetsAt`。如果预测曲线在重置前没有触顶，显示“重置时预计剩余 X 美元，占上限 Y%”。如果触顶，显示“预计在 R 之前 X 小时触顶”。

### 7.3 模型级耗尽时间

对模型组 `m` 和窗口 `w`：

```text
C_m,w(t) = 模型当前估算已用 + 到 t 的该模型预测增量
modelLimit_m,w = 模型月额度 × 窗口比例
t_exhaust_model(m,w) = min { t | C_m,w(t) >= modelLimit_m,w }
```

计划级约束另算：

```text
t_exhaust_plan(w) = min { t | U_w(t) >= planLimit_w }
```

模型上限和共享计划上限不能合并成一个“每个模型的较小上限”。共享额度是所有模型共同消耗的总表，模型额度只约束该模型。最终展示的最早风险为：

```text
t_risk = min[
  t_exhaust_plan(w) for each window,
  t_exhaust_model(m,w) for each model and window
]
```

对应的文案可能是：

- “GPT 5.6 Luna 周额度预计在 10 月 22 日 18:20 触顶，比 UTC 周重置早 3 天。”
- “DeepSeek V4.1 Flash 当前 5 小时窗口预计剩余 4.2 美元；共享 5 小时额度剩余 1.8 美元，共享额度更紧。”
- “月额度预计在 10 月 28 日触顶，重置时剩余为 0；当前计划已超出后自动使用余额。”

### 7.4 5 小时、周、月的窗口语义

三个窗口不能使用同一个重置算法：

- 5 小时窗口：以当前 meter 的 `startsAt` / `resetsAt` 为准。未开始时显示“首次使用后开始”，不伪造耗尽时间。
- 周窗口：按 UTC 日历周，使用 meter 的 `resetsAt`。
- 月窗口：按付费周期，使用 `month.resetsAt`，不能简单假设为每月 1 日或本地月末。

如果未来官方把 5 小时窗口改成连续滚动窗口，预测模块需要在计算时扣除即将离开窗口的旧事件。当前实现应先把窗口类型做成配置，不要把这个假设散落在 UI 代码中。

### 7.5 额外用量

如果 `useBalance` 已开启，额度触顶后请求会转向 Console 余额。预测组件要区分：

- `quota`：套餐额度消耗。
- `cash`：额度触顶后从余额支付的金额。

这种情况下，不能把“触顶”直接显示为“请求将失败”。应显示：

```text
预计 10 月 28 日触顶；触顶后预计从余额支付 $X
```

如果没有开启 `useBalance`，才显示“触顶后请求会被拦截”。

## 8. 组件设计

建议新增一个“用量预测”标签页，保留现有的性能图表和请求明细。组件分为五块。

### 8.1 顶部摘要卡

展示四个最常用的结论：

- “下一小时预计”：`p50`，附 `p10–p90`。
- “到重置预计”：当前计划的窗口剩余或预计总消耗。
- “最早风险”：模型名、窗口名、预计触顶时间。
- “套餐利用率”：计划月 meter 的百分比，附快照时间。

卡片同时显示“数据截止时间”和“置信度”。如果官方快照超过十分钟未更新，显示“快照较旧”，不要把它当成实时值。

### 8.2 计划 meter

用三条水平进度条展示：

```text
Rolling 5h   $8.20 / $12.00   68%   重置：18:40
Weekly       $19.50 / $30.00  65%   重置：10/21 00:00 UTC
Monthly      $42.00 / $60.00  70%   重置：11/01 00:00
```

每条 meter 同时画出：

- 实心部分：官方已用。
- 斜纹部分：预测到重置的增量。
- 红色标记：`p90` 预测会越界的位置。

预测条不要把“官方已用”和“本地已用”叠加。官方值是当前的基线，本地值只用于解释和模型级拆分。

### 8.3 模型额度表

表格按风险排序，展示：

| 模型 | 5h 已用/上限 | 周已用/上限 | 本月已用/模型上限 | 预计触顶 | 预计重置剩余 |
|---|---:|---:|---:|---|---:|
| GPT 5.6 Luna | 22% | 64% | 89% | 10/26 14:10 | $1.20 |
| DeepSeek V4.1 Flash | 18% | 35% | 48% | 共享 5h 先触顶 | $14.80 |

每一行同时显示模型自身额度和共享计划剩余量，并标注最早触发的是模型额度还是共享计划额度。未知模型单独一行显示“未定价”，不出现在风险排序的分子中。

### 8.4 预测图

沿用当前 SVG 图表风格，新增一条预测曲线：

- 历史部分：实线。
- 预测部分：虚线。
- 置信区间：半透明带。
- 当前时刻：竖直分界。
- 当前窗口重置：另一条竖直标记。

图表上方提供“预测到”选择器，允许在“下一小时 / 未来 24 小时 / 到 5h 窗口结束 / 到周重置 / 到本月重置”之间切换。下方提供“现金费用 / 套餐额度”切换，两个口径不共用 Y 轴。

### 8.5 状态和空态

组件需要明确显示以下状态：

- 还没有官方额度快照。
- 快照存在但当前数据已过期。
- 当前工作区没有 Go 套餐。
- 当前模型没有价格。
- 本地历史不足，无法估计周期。
- 官方已用和本地计算存在较大差额。
- 当前窗口尚未开始。
- 已经触顶且开启额外用量。

空态不能显示一组看似精确的 0。没有数据时只展示“无法估计”，并给出缺少的原因。

## 9. 代码结构建议

保持预测逻辑和 DOM 渲染分离，Panel 只负责取数、状态和布局。

```text
src/quota/catalog.ts       套餐价格表、模型组、版本和促销规则
src/quota/pricing.ts       单请求匹配价格并计算 quotaUsd
src/quota/snapshot.ts      官方 meter 快照的类型和归一化
src/forecast/series.ts     分桶、周期因子、EWMA、趋势、回测区间
src/forecast/quota.ts      计划窗口、模型窗口、耗尽时间和剩余量
src/ui/forecast.ts         摘要卡、meter、模型表、预测图
src/types.ts               新增 QuotaSnapshot、ForecastPoint、QuotaRisk 等类型
src/api.ts                 获取套餐状态，沿用同源 Cookie
src/ui/panel.ts            新增 forecast tab 和取数状态
src/i18n.ts                中英文文案
src/ui/styles.ts           预测组件样式
```

数据层建议增加两个纯函数边界：

```ts
priceRecord(catalog, plan, record): PricedRecord
forecastQuota({ records, snapshot, catalog, now, horizon }): QuotaForecast
```

这样可以先用合成请求测试价格和额度逻辑，再接入 UI。

### 9.1 取数逻辑

当前 `reloadRecords` 只按当前展示范围取记录。预测页需要独立的取数范围：

- 现金预测：至少取最近 28 天，或者当前范围更大时取当前范围。
- 套餐额度：取当前 5 小时窗口、UTC 周窗口和付费周期的并集。
- 官方 meter：打开预测页或点击刷新时请求一次，缓存到 `meta`，键可以按工作区区分。
- 价格目录：按版本缓存，价格变更时使旧的预测结果失效。

请求日志和官方 meter 的时间不能相差太大。理想状态是同一时间点拉取，至少记录两个时间戳，UI 显示快照年龄。

### 9.2 结果缓存

预测结果可以按以下键缓存：

```text
workspaceID + latestRecordTimestamp + catalogVersion + snapshotCapturedAt + horizon + filters
```

价格折算结果按请求 `key` 缓存，价格表版本变化时清除。请求量较大时不需要每次渲染都重新匹配全部模型。

## 10. 实施顺序

第一阶段先做“可解释的额度和现金对照”：

1. 建立 PlanCatalog 和模型别名映射。
2. 实现单请求 `quotaUsd` 计算。
3. 接入官方 `fiveHour`、`week`、`month` meter。
4. 增加模型级已用估算和覆盖率提示。
5. 在 UI 中显示真实 meter 和简单的最近速率 ETA。

第二阶段加入预测引擎：

1. 实现 5 分钟、小时、天分桶。
2. 实现周期因子、EWMA 和置信区间回测。
3. 按当前视图调整默认预测跨度。
4. 增加预测图和模型级耗尽时间。

第三阶段做校准和产品化：

1. 用真实请求核对 `quotaUsd` 与官方 meter 增量。
2. 加入促销有效期和价格版本更新。
3. 增加额外用量、快照过期、历史缺口状态。
4. 对异常模型和价格变化提供用户可见的提示。

如果时间有限，第一阶段和第二阶段之间必须保留“官方 meter 为准”的边界。先做准确的当前状态，再叠加预测，避免预测建立在错误的价格口径上。

## 11. 需要验证的问题

以下问题应在实现前用真实请求和官方 meter 增量核对：

1. 请求日志的 `cost` 是普通按量费用，还是已经包含 Go 套餐折算；还是两者在某些请求上相同。
2. `reasoningTokens` 是否计入 output 价格，是否存在重复计数。
3. 上下文阈值使用 input、缓存读、缓存写的哪一个合计值，是否包含 output。
4. 模型额度组是否严格按文档表格执行，以及模型上限和共享计划上限的优先级。
5. 5 小时窗口是“首次使用后的固定 5 小时”还是连续滚动窗口；以 `startsAt` / `resetsAt` 为准。
6. 周窗口是否严格按 UTC 周，月窗口是否严格按付费周期。
7. 促销额度（如限时 2x、4x）的有效期和失效后的回退值。
8. 请求失败、拒绝、取消时是否计入额度；官方 meter 增量是最终判断依据。
9. 额外用量开启后，请求日志的 `cost` 与余额扣减是否一致。
10. 控制台状态接口的字段是否稳定，是否需要为旧版本保留 DOM 或请求捕获的回退路径。

## 12. 验收标准

组件完成后，至少满足以下行为：

- 1 小时视图显示“过去 1 小时 + 下一小时”的预测，而不是把一小时消费乘以 24。
- 24 小时视图按未来每个小时的周期因子预测，而不是拿昨天的总量直接复制。
- 30 天视图预测到实际月重置时间，显示 `p50` 和 `p90` 两种情况。
- DeepSeek 和 GPT 使用各自的价格变体，模型额度与共享额度同时生效。
- 5 小时、UTC 周、付费周期三个窗口分别显示已用、上限、重置时间和预测。
- 官方 meter 可用时，计划级已用以官方值为基线。
- 未知模型、历史缺口、快照过期不会被静默当作 0。
- 现金费用和套餐额度可以用不同颜色、不同标签和独立切换查看。
